# คู่มืออธิบายระบบ MUT Bus Booking — เตรียมตอบคำถามอาจารย์

เอกสารนี้อธิบายทั้งหัวข้อในภาพประเมิน “ระบบบังคับทำ (20 คะแนน)” และภาพรวมการทำงานของระบบจากโค้ดปัจจุบัน ใช้สำหรับทบทวนและสาธิตระบบ ไม่ใช่การรับรองคะแนนล่วงหน้า เพราะการให้คะแนนขึ้นกับเกณฑ์ย่อยและการทดสอบของผู้สอน

> **ข้อควรรู้ด้านความปลอดภัย:** การซ่อนพนักงานในหน้าเว็บปัจจุบันเป็นการซ่อนจากรายการ ไม่ได้ปิดบัญชีเข้าสู่ระบบ หากเป็นระบบใช้งานจริง ควรยืนยันนโยบายว่าการซ่อน/เลิกจ้างต้องระงับบัญชีด้วยหรือไม่

## 1. อ่านตารางคะแนนในภาพอย่างไร

ภาพแบ่งงานหลัก 3 กลุ่ม รวม 20 คะแนน:

| กลุ่ม | ส่วนโปรแกรม | ส่วนตอบคำถาม | รวม |
|---|---:|---:|---:|
| Login / Logout ตามสิทธิ์ที่กำหนด | 4 | 2 | 6 |
| Dynamic RBAC เพิ่ม–ลบ–แก้ไข–ค้นหา | 4 | 3 | 7 |
| จัดการพนักงาน เพิ่ม–ลบ–แก้ไข–ค้นหา | 4 | 3 | 7 |
| **รวม** | **12** | **8** | **20** |

หัวตารางบอกคะแนนของ “โปรแกรม” และ “ตอบคำถาม” แยกกัน แต่ช่องย่อยในภาพไม่ได้แสดงรายละเอียด rubric ว่าแต่ละพฤติกรรมให้คะแนนย่อยเท่าไร จึงควรอธิบายเหตุผลการออกแบบและสาธิตให้เห็นการทำงานจริง ไม่ควรเดาคะแนนย่อยแทนอาจารย์

## 2. ภาพรวมระบบ

ระบบแบ่งเป็น 3 ส่วนที่ทำงานร่วมกัน:

1. **หน้าเว็บ:** React + TypeScript แสดงหน้าผู้โดยสาร คนขับ และผู้ดูแลระบบ
2. **API:** Express รับคำขอจากเว็บ ตรวจข้อมูลและสิทธิ์ แล้วเรียกฐานข้อมูล
3. **Oracle:** เก็บบัญชี บุคลากร ตำแหน่ง หน้าจอ สิทธิ์ และข้อมูลการเดินรถ/จอง

เมื่อใช้ API mode การเพิ่มหรือแก้ไขที่รองรับจะส่งคำขอไป API และเขียน Oracle ก่อนสะท้อนผลกลับบนเว็บ ส่วนโหมดตัวอย่าง/ออกแบบบางส่วนยังใช้ข้อมูลจำลอง จึงควรสาธิตหลังล็อกอินแบบ API เพื่อแสดงการทำงานฐานข้อมูลจริง

**ตัวอย่างการไหลของคำขอ:**

`ผู้ใช้กดปุ่ม → React เรียก /api/... → Express ตรวจ token/สิทธิ์/ข้อมูล → Oracle SELECT/INSERT/UPDATE → API ส่งผล → หน้าเว็บอัปเดต`

## 3. Login และ Logout ตามสิทธิ์ — 6 คะแนนตามหัวตาราง

### 3.1 ระบบแยกบทบาท

ระบบมีบทบาทหลัก:

- **ผู้โดยสาร:** สมัคร/ล็อกอิน ดูรอบรถ จองและดูรายการตั๋วของตนเอง
- **พนักงานขับรถ:** ดูรอบที่ได้รับมอบหมาย ดูรายชื่อผู้โดยสาร เริ่มงาน ตรวจตั๋ว/เช็กอิน และปิดรอบ
- **ผู้ดูแลระบบ:** จัดการบุคลากร สิทธิ์ รอบรถ และข้อมูลดูแลระบบตามสิทธิ์

แต่ละบทบาทมี endpoint ล็อกอินต่างกัน (`/api/auth/passenger/login`, `/api/auth/driver/login`, `/api/auth/admin/login`) ตัว API ค้นหาบัญชีใน Oracle แล้วตรวจรหัสผ่าน ไม่ได้เชื่อรหัสผ่านที่ส่งมาจากหน้าเว็บอย่างเดียว

### 3.2 การเก็บและตรวจรหัสผ่าน

- รหัสผ่านไม่ถูกเก็บเป็นข้อความปกติ แต่แฮชด้วย `scrypt` พร้อม salt
- เมื่อเข้าสู่ระบบ API อ่าน `PASSWORD_HASH` แล้วตรวจด้วยฟังก์ชัน verify แบบเปรียบเทียบอย่างปลอดภัย
- สมัครผู้โดยสารจากหน้าเว็บกำหนดอีเมล `@mut.ac.th` เป็นทั้ง username และ email และกำหนดรหัสผ่านอย่างน้อย 8 ตัวอักษร
- การสมัครผู้โดยสารไม่ได้สร้างพนักงานหรือผู้ดูแลระบบ บัญชีพนักงานต้องสร้างผ่านการจัดการพนักงาน

### 3.3 การกำหนดสิทธิ์

สิทธิ์อิงความสัมพันธ์ระหว่าง **ตำแหน่ง (POSITION)** กับ **หน้าจอ (SCREEN)** ผ่านตารางกลาง **ROLE_PERMISSION**:

- `CAN_VIEW = Y` หมายถึงดูหน้าจอได้
- `CAN_EDIT = Y` หมายถึงแก้ไขได้ และต้องเปิดสิทธิ์ดูด้วย
- หน้าเว็บใช้สิทธิ์เพื่อแสดง/ปิดปุ่มและแท็บ
- API ตรวจสิทธิ์ซ้ำที่ฝั่งเซิร์ฟเวอร์ในรายการแก้ไขสำคัญ ไม่ได้พึ่งการซ่อนปุ่มอย่างเดียว
- คนขับต้องมีสิทธิ์หน้าจอรหัส `8820`
- ผู้ดูแลระบบต้องมีสิทธิ์ดูหน้าจอจัดการอย่างน้อยหนึ่งรหัสใน `1101`, `1102`, `1103`; การแก้ไขแต่ละชุดตรวจ `CAN_EDIT` ของหน้าจอที่ตรงกัน

**ประโยคตอบอาจารย์:** “เราใช้ RBAC โดยผู้ใช้พนักงานผูกกับตำแหน่ง ตำแหน่งผูกกับหน้าจอผ่าน ROLE_PERMISSION และแยกสิทธิ์ดู/แก้ไข ระบบตรวจทั้งหน้าเว็บเพื่อประสบการณ์ใช้งานและตรวจซ้ำที่ API เพื่อไม่ให้เรียกแก้ไขข้ามสิทธิ์ได้ง่าย”

### 3.4 Logout และอายุ session

- เมื่อล็อกอินสำเร็จ API คืน Bearer token
- ฝั่งเว็บเก็บ token ใน `sessionStorage` และแนบไปกับ API requests
- Logout เรียก API เพื่อลบ session และล้าง token ฝั่งเว็บ
- Session ปัจจุบันเก็บในหน่วยความจำ API มีอายุ 12 ชั่วโมง ดังนั้นการ restart API ทำให้ session ที่ยังไม่หมดอายุหายไปด้วย

## 4. Dynamic RBAC — 7 คะแนนตามหัวตาราง

หน้า “ตารางสิทธิตามตำแหน่ง” แสดงสิทธิ์จัดกลุ่มตามตำแหน่ง มีตัวกรองตำแหน่งและช่องค้นหาชื่อตำแหน่ง ชื่อหน้าจอ หรือ screen code

### เพิ่มสิทธิ์

1. เลือกตำแหน่ง
2. เลือกหน้าจอ
3. กำหนดสิทธิ์ดูและแก้ไข
4. บันทึก
5. API ใช้ `MERGE` ใน Oracle: ถ้ามีคู่ตำแหน่ง–หน้าจอแล้วจะอัปเดต ถ้ายังไม่มีจะเพิ่ม จึงเรียกได้ทั้งเพิ่มหรือบันทึกทับสิทธิ์เดิม

ข้อกำหนดสำคัญ: เปิดแก้ไขไม่ได้ถ้าไม่ได้เปิดดู เพื่อรักษาเงื่อนไข `CAN_EDIT` ต้องไม่เป็น Y เมื่อ `CAN_VIEW` เป็น N

### แก้สิทธิ์

ปุ่มสลับ “ดู” และ “แก้ไข” ส่งค่าชุดใหม่ไป API แล้วให้ Oracle upsert เมื่อปิดสิทธิ์ดู ระบบปิดสิทธิ์แก้ไขตามไปด้วย ผลใน UI อัปเดตหลัง API ตอบสำเร็จ

### ลบสิทธิ์

คำว่า “ลบ” ใน UI เป็นการ **ซ่อนจากหน้าจัดการ** ไม่ได้ DELETE แถว `ROLE_PERMISSION` ทิ้ง ระบบบันทึก marker ใน `WEB_HIDDEN_RECORD` และไม่แสดงสิทธิ์ที่ถูกซ่อนในรายการแอดมิน ตัวตรวจสิทธิ์ backend ไม่นับ permission ที่ถูกซ่อนด้วย ข้อมูลเดิมยังคงอยู่ใน Oracle

### ค้นหา

กรองได้จากตำแหน่ง หน้าจอ และรหัสหน้าจอ เช่น `9102` จึงค้นหาว่าตำแหน่งใดมีสิทธิ์เข้าถึงหน้าจอที่สนใจได้

## 5. จัดการพนักงาน — 7 คะแนนตามหัวตาราง

หน้า “พนักงาน & ยานพาหนะ” มีแท็บพนักงานและยานพาหนะ ในกลุ่มคะแนนนี้ให้เน้นการจัดการพนักงาน

### เพิ่มพนักงาน

กรอกชื่อ username รหัสผ่าน เบอร์โทร อีเมล ฝ่าย/แผนก และตำแหน่ง จากนั้นเว็บเรียก `POST /api/admin/employees`:

- API ตรวจสิทธิ์แก้ไขหน้าจอพนักงาน (`1101`)
- ตรวจความยาว/ข้อมูลจำเป็น รหัสผ่านขั้นต่ำ 8 ตัวอักษร และรูปแบบอีเมลเมื่อมีค่า
- สร้างรหัสพนักงานและ hash รหัสผ่าน
- INSERT ลง Oracle ตาราง `EMPLOYEE`
- ส่งข้อมูลพนักงานที่บันทึกกลับมาให้หน้าเว็บแสดง

### แก้ไขพนักงาน

เลือกไอคอนแก้ไข เปลี่ยนข้อมูล แล้วบันทึกผ่าน `PUT /api/admin/employees/:employeeId` API ล็อกแถวเดิม ตรวจรหัสแผนก/ตำแหน่ง และเปลี่ยน hash เฉพาะกรณีมีการกำหนดรหัสผ่านใหม่ หากไม่กรอกรหัสผ่านเดิมจะคงอยู่

### ลบ/ซ่อนพนักงาน — จุดที่ควรอธิบายให้ชัด

ใน API mode การกดลบสร้างรายการซ่อนใน `WEB_HIDDEN_RECORD` แล้วเอาพนักงานออกจากรายการเว็บแอดมิน โดย **ไม่ลบแถว `EMPLOYEE` ใน Oracle** ตามแนวทางเก็บประวัติข้อมูล

อย่างไรก็ตาม ปัจจุบันการซ่อนพนักงานไม่ได้เปลี่ยน `EMPLOYEE.IS_ACTIVE` และ endpoint login เช็ก `IS_ACTIVE = 'Y'` เท่านั้น ดังนั้นพนักงานที่ซ่อนยังอาจล็อกอินได้ นี่เป็นข้อจำกัด/ข้อพิจารณาด้านนโยบาย ไม่ควรอธิบายว่าการกดลบคือการปิดบัญชี ถ้าผู้สอนต้องการให้ล็อกอินไม่ได้ ต้องเพิ่มการ deactivate แยกจากการซ่อน หรือกำหนดนโยบายการลบให้ชัดเจน

### ค้นหาพนักงาน

ช่องค้นหากรองข้อมูลที่โหลดมาแล้วจากรหัสพนักงาน ชื่อ username เบอร์โทร อีเมล ชื่อตำแหน่ง และเลขฝ่าย ช่วยให้ค้นหาบุคลากรในรายการได้เร็ว

## 6. ข้อมูลอื่นในหน้า Admin ที่ช่วยเล่าภาพรวม

ระบบยังมีการจัดการฝ่าย/แผนก ตำแหน่ง ยานพาหนะ ประเภทรถ และรอบรถ รวมถึง:

- สร้างและแก้ไขฝ่าย/แผนกและตำแหน่งใน Oracle; การลบจากหน้าเว็บเป็นการซ่อน ไม่ลบแถว
- สร้างพนักงานและยานพาหนะใน Oracle
- สร้างหลายรอบรถพร้อมตรวจคนขับ/รถชนเวลาผ่าน API
- ยกเลิก/เปิดรอบที่ยังไม่เริ่ม โดยอัปเดต `TRIP.STATUS`
- ตรวจเช็กอินคนขับและสรุปผู้โดยสาร

เส้นทางแสดงชื่อ ลำดับจุดจอด และเวลาเดินทาง แต่หน้าเส้นทางปัจจุบันเป็นหน้าอ่านข้อมูลเป็นหลัก ไม่ควรกล่าวว่าหน้านี้รองรับ CRUD เส้นทางและจุดจอดครบแล้ว

## 7. ภาพรวมฝั่งผู้โดยสารและคนขับ

### ผู้โดยสาร

- เลือกเส้นทาง วันที่ จุดขึ้น และจุดลง
- แสดงรอบที่เปิดใช้และคำนวณเวลาถึงจุดขึ้น/ลงจากเวลาเริ่มรอบและเวลาระหว่างจุดจอด
- ระบบกำหนดให้จองก่อนถึงจุดขึ้นอย่างน้อย 20 นาที และจำกัดไม่เกิน 4 ที่นั่งต่อรายการ
- API ตรวจ cutoff, ลำดับจุดจอด, ความจุ และล็อกรอบรถขณะบันทึก เพื่อป้องกันจองเกิน
- ยกเลิกการจองเป็นการเปลี่ยนสถานะรายการ ไม่ใช่ลบประวัติ
- ซ่อนตั๋วในหน้าเว็บเป็น marker เฉพาะผู้โดยสารคนนั้น ข้อมูลการจองใน Oracle ยังคงอยู่

### คนขับ

- ดูเที่ยวที่ได้รับมอบหมายและรายชื่อผู้โดยสาร
- เริ่มเที่ยว ตรวจ QR/booking code เพื่อเช็กอิน และปิดเที่ยว
- API ตรวจสิทธิ์หน้าจอคนขับและบันทึกสถานะการเดินทาง/การเช็กอินใน Oracle

## 8. ตาราง Oracle ที่ควรรู้เวลาอธิบาย

| ตาราง | หน้าที่โดยย่อ |
|---|---|
| `SYSTEM_USER` | บัญชีผู้โดยสารและ hash รหัสผ่าน |
| `EMPLOYEE` | พนักงาน คนขับ และผู้ดูแลระบบ |
| `POSITION` | ตำแหน่งงาน |
| `DEPARTMENT` | ฝ่าย/แผนก |
| `SCREEN` | รายการหน้าจอและ screen code |
| `ROLE_PERMISSION` | สิทธิ์ดู/แก้ไขของแต่ละตำแหน่งต่อแต่ละหน้าจอ |
| `WEB_HIDDEN_RECORD` | marker ซ่อนข้อมูลจากเว็บโดยไม่ลบแถวต้นฉบับ |
| `ROUTE`, `STOP`, `ROUTE_STOP` | เส้นทาง จุดจอด และลำดับ/เวลาระหว่างจุด |
| `VEHICLE`, `VEHICLE_TYPE` | รถและประเภทรถ |
| `TRIP` | รอบรถและสถานะการเดินทาง |
| `BOOKING`, `BOOKING_DETAIL` | หัวรายการจองและรายละเอียดเที่ยว/จำนวนที่นั่ง/สถานะ |

## 9. คำตอบสั้นสำหรับคำถามที่อาจารย์อาจถาม

**ถาม: ถ้าซ่อนสิทธิ์แล้ว สิทธิ์ยังอยู่ไหม?**  
ตอบ: แถว ROLE_PERMISSION ยังอยู่ใน Oracle แต่มี visibility marker ทำให้ไม่แสดงในหน้าเว็บ และ API ไม่นับสิทธิ์ที่ซ่อน

**ถาม: ถ้าลบพนักงานแล้วข้อมูลหายไหม?**  
ตอบ: ไม่ลบแถว EMPLOYEE; ซ่อนจากรายการแอดมินด้วย WEB_HIDDEN_RECORD แต่ปัจจุบันไม่ได้ปิด IS_ACTIVE จึงยังอาจล็อกอินได้ เป็นข้อจำกัดที่ควรปรับตามนโยบายความปลอดภัย

**ถาม: ป้องกันผู้ไม่มีสิทธิ์แก้ข้อมูลอย่างไร?**  
ตอบ: หน้าเว็บแสดงปุ่มตามสิทธิ์ และ API ตรวจ Bearer session กับ ROLE_PERMISSION.CAN_EDIT ซ้ำที่ server

**ถาม: ป้องกันเก็บรหัสผ่านตรง ๆ อย่างไร?**  
ตอบ: ใช้ scrypt พร้อม salt เก็บ password hash และตรวจรหัสด้วย verify แทนการเทียบ/เก็บ plaintext

**ถาม: คำว่า dynamic หมายถึงอะไร?**  
ตอบ: เพิ่มหรือปรับคู่ตำแหน่ง–หน้าจอและสิทธิ์ดู/แก้ไขในตารางได้โดยไม่ต้องสร้างหน้าจอใหม่ต่อบทบาทแบบ hard-code ทั้งหมด การตรวจสิทธิ์ใช้ screen code และข้อมูล permission จาก Oracle

**ถาม: ทดสอบว่าอัปเดตลงฐานข้อมูลจริงได้อย่างไร?**  
ตอบ: เข้าสู่ระบบผ่าน API เปิด Network/ดู API response แล้วโหลดข้อมูลใหม่จาก Oracle หรือออกและเข้าใหม่เพื่อดูข้อมูล master ที่โหลดจาก `/api/admin/masters` ทั้งนี้ต้องเชื่อม Oracle และให้ schema/migration ครบก่อน

## 10. บทพูดสาธิตประมาณ 1 นาที

“ระบบแบ่งผู้ใช้เป็นผู้โดยสาร คนขับ และผู้ดูแลระบบ การเข้าสู่ระบบตรวจบัญชีและ hash รหัสผ่านใน Oracle จากนั้นออก session token ผู้ดูแลกำหนดสิทธิ์แบบ RBAC โดยจับคู่ตำแหน่งกับหน้าจอผ่าน ROLE_PERMISSION และแยกสิทธิ์ดูและแก้ไข หน้าเว็บใช้ควบคุมการแสดงเมนู ส่วน API ตรวจสิทธิ์ซ้ำก่อนแก้ข้อมูล ในหน้าพนักงาน ผู้ดูแลเพิ่ม แก้ไข ค้นหา และซ่อนข้อมูลได้ การเพิ่มและแก้ไขส่งไป API เพื่อบันทึก Oracle ส่วนการซ่อนเก็บ marker แยกไว้ ไม่ลบข้อมูลต้นฉบับ สำหรับบัญชีพนักงานที่ซ่อน ปัจจุบันยังไม่ได้ปิดการล็อกอิน จึงเป็นจุดที่สามารถต่อยอดให้ตรงนโยบายความปลอดภัยได้ครับ/ค่ะ”

## 11. ข้อจำกัดที่ควรพูดอย่างตรงไปตรงมา

- รายงานสถิติบางส่วนยังใช้ข้อมูลตัวอย่าง ไม่ใช่ผล aggregate จาก Oracle
- หน้าจัดการเส้นทาง/จุดจอดยังไม่ได้ทำ CRUD ครบ
- การซ่อนพนักงานไม่ปิดบัญชี login ณ ปัจจุบัน
- Session เก็บในหน่วยความจำ API และหายเมื่อ restart
- คะแนนจริงขึ้นกับ rubric ฉบับเต็มและการสาธิต ไม่สามารถสรุปจากหัวตารางอย่างเดียว
