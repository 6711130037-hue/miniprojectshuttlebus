หัวข้อ 1 · ระบบการจอง

ตรวจสอบเงื่อนไขการจอง

การจองและตรวจสอบเงื่อนไขต่าง ๆ ในการจอง

1ก่อนบันทึกการจอง ระบบตรวจสอบอะไรบ้าง?

แนวตอบ: ตรวจว่ารอบยังเปิดจอง จุดขึ้นและจุดลงอยู่ในเส้นทางเดียวกันและจุดขึ้นมาก่อนจุดลง ตรวจเวลาถึงจุดขึ้นต้องเหลืออย่างน้อย 20 นาที จำนวนที่นั่งไม่เกิน 4 และความจุรถยังพอ

2ทำไมต้องตรวจเวลาถึง “จุดขึ้น” ไม่ใช่ดูแค่เวลาออกรถ?

แนวตอบ: ผู้โดยสารอาจขึ้นกลางเส้นทาง เวลาถึงจุดขึ้นจึงเท่ากับเวลาออกบวกเวลาสะสมจากจุดก่อนหน้า ระบบใช้เวลานี้ตรวจ cutoff 20 นาทีอย่างเหมาะสมกับผู้โดยสารแต่ละจุด

3ป้องกันผู้โดยสารหลายคนจองจนเกินความจุพร้อมกันอย่างไร?

แนวตอบ: API เปิด transaction และล็อกแถวรอบรถก่อนคำนวณยอดที่นั่งที่ยังไม่ยกเลิก แล้วตรวจยอดเดิมบวกจำนวนที่ขอเทียบกับความจุ จึงลด race condition จากการจองพร้อมกัน

4ตอนนี้จองล่วงหน้าได้กี่วัน และถ้าเรียก API ข้ามหน้าจอจะเกิดอะไร?

แนวตอบ: จองได้เฉพาะวันนี้หรือพรุ่งนี้ UI จำกัดวันที่และ API ตรวจซ้ำจากวันที่ให้บริการแบบเวลาไทย (Asia/Bangkok) คำขอวันที่อื่นถูกปฏิเสธ แม้พยายามข้าม UI

หัวข้อ 2 · ระบบการจอง

ออก QR Code และดูรอบที่จะเดินทาง

สร้าง QR หลังจองสำเร็จและใช้งานกับรอบรถ

5เมื่อจองสำเร็จ QR Code บรรจุข้อมูลอะไร?

แนวตอบ: ใน API mode QR บรรจุ booking code ที่ API ออกให้ ไม่ใช่ข้อมูลส่วนตัวทั้งหมด คนขับส่งค่านี้กลับไปตรวจรายการจองกับรอบรถในฐานข้อมูล

6ถ้ามีหลายเที่ยวหรือจองหลายที่นั่ง จัดการ QR อย่างไร?

แนวตอบ: แต่ละ booking/รายละเอียดเที่ยวมีตัวระบุที่ผูกกับ booking code และ trip จึงตรวจได้ว่า QR ใช้กับเที่ยวใด จำนวนที่นั่งเป็น seat_count ของรายการ ไม่ได้สร้างชื่อหรือ QR แยกให้ทุกที่นั่ง

7ทำไม QR จึงไม่ควรเปิดเผยชื่อ เบอร์โทร หรือรายละเอียดผู้โดยสารไว้ตรง ๆ?

แนวตอบ: ลดการเปิดเผยข้อมูลส่วนบุคคล QR ควรมีเพียงรหัสอ้างอิงที่คาดเดายาก แล้วให้ server ตรวจสิทธิ์และสถานะจากฐานข้อมูล

8จะแสดง QR ของเที่ยวในอนาคตและจัดการ QR ที่ใช้แล้วอย่างไร?

แนวตอบ: ผู้โดยสารเปิด boarding pass จากรายการจองที่ยังใช้ได้ รายการที่จะถึงคำนวณจากเวลาที่รถถึงจุดขึ้น ส่วน QR ที่เช็กอิน ยกเลิก หรือเที่ยวเสร็จแล้วแสดงสถานะและไม่ควรใช้เช็กอินซ้ำ

หัวข้อ 3 · ระบบการจอง

ยกเลิกและคืนที่นั่ง

ยกเลิกตามเงื่อนไขและคืนจำนวนที่นั่งให้รอบรถ

9ยกเลิกการจองได้เมื่อใด?

แนวตอบ: API อนุญาตให้ยกเลิกเฉพาะ booking ที่ยังยืนยันและรอบรถยังเปิด (สถานะ 1) ถ้ารอบเริ่มแล้วหรือรายการไม่อยู่สถานะที่ยกเลิกได้ ระบบตอบข้อผิดพลาด

10ระบบ “คืนที่นั่ง” อย่างไรเมื่อยกเลิก?

แนวตอบ: ไม่ลบ booking แต่เปลี่ยน STATUS_CODE เป็น 0 การคำนวณผู้โดยสาร/ความจุไม่นับรายการสถานะ 0 จึงนำที่นั่งกลับมาเปิดจอง

11ทำไมเก็บรายการยกเลิกไว้ แทนการ DELETE?

แนวตอบ: เพื่อรักษาประวัติการทำรายการ ตรวจสอบย้อนหลังและรองรับ audit ขณะเดียวกันสถานะยกเลิกแยกจากรายการที่ยังใช้งาน

12ถ้าผู้โดยสารกดยกเลิกสองครั้งหรือมีการยกเลิกพร้อมกัน ระบบควรทำอย่างไร?

แนวตอบ: endpoint เปลี่ยนเฉพาะรายการสถานะยืนยันและล็อกแถวที่เกี่ยวข้อง การเรียกซ้ำจึงไม่ควรคืนที่นั่งซ้ำหรือทำให้จำนวนว่างเกินจริง และควรแจ้งสถานะล่าสุดให้ผู้ใช้ทราบ

หัวข้อ 4 · ระบบคนขับ

ตารางงานรายวัน

แสดงเที่ยวที่ได้รับมอบหมายในแต่ละวัน

13คนขับเห็นรอบรถใดบ้าง?

แนวตอบ: เห็นรอบที่ DRIVER_ID ตรงกับบัญชีคนขับและตรงกับวันที่เลือก หน้าจอมีตัวเลือกดูวันนี้หรือพรุ่งนี้ และแสดงจำนวนรอบกับรายละเอียดเวลา เส้นทาง และรถ

14การดูตารางพรุ่งนี้เปลี่ยนเที่ยวที่กำลังสแกนของวันนี้หรือไม่?

แนวตอบ: ไม่เปลี่ยน ตารางพรุ่งนี้เป็นโหมดดูอย่างเดียว ส่วนเที่ยวปฏิบัติงานและการสแกนยังยึดเที่ยวของวันนี้ เพื่อป้องกันเริ่มงานหรือเช็กอินผิดวัน

15ถ้าคนขับไม่เห็นรอบที่คิดว่าได้รับมอบหมาย จะตรวจอะไร?

แนวตอบ: ตรวจวันให้บริการ รหัสพนักงานใน DRIVER_ID สถานะการมอบหมาย และบัญชีที่ล็อกอิน จากนั้นตรวจ API /driver/trips ซึ่งคืนเฉพาะเที่ยวของคนขับที่ยืนยันตัวตน

16เหตุใดการแสดงวันที่ในงานขนส่งควรระวัง timezone?

แนวตอบ: timestamp ของเที่ยวอาจถูกแปลงเป็นอีกวันหากตีความเป็น UTC แต่ตารางเดินรถเป็นเวลาท้องถิ่น จึงต้องใช้เขตเวลาให้สอดคล้องและสร้าง date key จากวันปฏิทินที่ต้องการ

หัวข้อ 5 · ระบบคนขับ

เริ่มเที่ยวและข้อมูลผู้โดยสารตามจุดจอด

เริ่มงานและดูข้อมูลผู้โดยสารขึ้น–ลงตามจุด

17เมื่อคนขับกด “เริ่มออกรถ” ระบบเปลี่ยนอะไร?

แนวตอบ: API ตรวจว่าคนขับได้รับมอบหมายและรอบยังเปิด จากนั้นเปลี่ยนสถานะเที่ยวเป็นกำลังเดินทางและบันทึกเวลาเริ่มจริง การทำรายการต้องผ่านสิทธิ์แก้ไขของหน้าจอคนขับ

18ระบบรู้ได้อย่างไรว่าผู้โดยสารควรขึ้นหรือลงที่จุดใด?

แนวตอบ: รายละเอียดการจองเก็บ pickup_route_stop_id และ dropoff_route_stop_id ซึ่งอ้างถึงจุดจอดตามลำดับในเส้นทาง จึงจัดกลุ่มรายการขึ้น/ลงแยกแต่ละจุดได้

19ทำไมใช้ route_stop_id แทน stop_id อย่างเดียว?

แนวตอบ: เส้นทางเดียวอาจผ่านสถานที่เดิมมากกว่าหนึ่งครั้ง เช่น ออกและกลับมหาวิทยาลัย route_stop_id ระบุครั้งและลำดับที่แน่นอน ส่วน stop_id ระบุเพียงสถานที่ทางกายภาพ

20ถ้าจอง 3 ที่นั่ง ระบบรู้ชื่อผู้โดยสารทั้ง 3 คนหรือไม่?

แนวตอบ: ไม่รู้จากข้อมูลปัจจุบัน เพราะเก็บหนึ่ง booking กับ seat_count 3 ไม่ได้เก็บตัวตนรายที่นั่ง ระบบจึงแสดงชื่อเจ้าของรายการและจำนวน 3 ที่นั่ง ไม่แต่งชื่อผู้โดยสารเพิ่ม

หัวข้อ 6 · ระบบคนขับ

สแกน QR และเช็กอิน

สแกน QR Code ของผู้โดยสาร

21อธิบายขั้นตอนเช็กอินด้วย QR ตั้งแต่ต้นจนจบ

แนวตอบ: คนขับเลือกรอบที่กำลังวิ่ง เปิดกล้องหรือป้อน booking code ระบบส่งค่าไป API ตรวจว่ารหัสตรงกับ booking ในเที่ยวนี้และยังยืนยัน ก่อนบันทึกสถานะเช็กอินพร้อมเวลาและผู้ตรวจ

22ถ้านำ QR ของอีกเที่ยวมาสแกนจะเกิดอะไร?

แนวตอบ: API ค้น booking code พร้อม trip_id และสถานะยืนยัน ถ้าไม่ตรงเที่ยวหรือไม่ถูกต้องจะปฏิเสธ จึงไม่ยอมรับเพียงเพราะ QR มีรูปแบบถูกต้อง

23ระบบป้องกันการสแกน QR เดิมซ้ำอย่างไร?

แนวตอบ: การเช็กอินเปลี่ยนสถานะจากยืนยันเป็นเช็กอินแล้ว คำขอถัดไปค้นเฉพาะสถานะยืนยัน จึงไม่พบรายการและตอบปฏิเสธการเช็กอินซ้ำ

24ถ้ากล้องใช้ไม่ได้ คนขับยังเช็กอินได้หรือไม่?

แนวตอบ: ได้ โดยป้อน booking code ด้วยตนเอง กล้องต้องใช้ secure context เช่น localhost/HTTPS และได้รับอนุญาตจาก browser ส่วน API ยังตรวจรหัสและเที่ยวเหมือนเดิม

หัวข้อ 7 · ระบบคนขับ

จบเที่ยวและสรุปยอด

จบงานและสรุปผู้โดยสารที่มาใช้บริการจริง

25เมื่อกดปิดรอบ ระบบสรุปสถานะอย่างไร?

แนวตอบ: เมื่อเที่ยวกำลังเดินทาง ระบบเปลี่ยนรายการที่เช็กอินแล้วเป็นเสร็จสิ้น และรายการยืนยันที่ยังไม่เช็กอินเป็น no-show จากนั้นเปลี่ยนสถานะเที่ยวเป็นเสร็จสิ้น

26“จำนวนผู้โดยสารจริง” ในรายงานปัจจุบันคำนวณจากอะไร?

แนวตอบ: คำนวณจากผลรวม seat_count ของ booking ที่เช็กอินแล้ว ไม่ใช่การนับ booking อย่างเดียว เพราะหนึ่ง booking อาจจองหลายที่นั่ง

27ข้อจำกัดของคำว่า “มาใช้บริการจริง” ในระบบตอนนี้คืออะไร?

แนวตอบ: ระบบยืนยันการขึ้นรถจาก check-in แต่ยังไม่มี event ยืนยันว่าลงรถจริงรายบุคคลหรือรายจุด สรุปจึงเป็นจำนวนที่เช็กอิน ไม่ใช่การติดตามขึ้น–ลงทางกายภาพครบทุกช่วง

28ทำไมต้องแยกผู้เช็กอินกับ no-show ก่อนสรุปเที่ยว?

แนวตอบ: เพื่อให้แยกผู้ที่ขึ้นรถตามการยืนยันออกจากผู้ที่จองแต่ไม่มา ช่วยสรุปจำนวนผู้ใช้บริการและรักษาสถานะ booking ให้ตรวจสอบย้อนหลังได้

หัวข้อ 8 · ตารางเหลือง

เข้าสู่ระบบและออกจากระบบตามสิทธิ์

Authentication, session และบทบาทผู้ใช้งาน

29ระบบแยกผู้โดยสาร คนขับ และผู้ดูแลระบบอย่างไร?

แนวตอบ: แยก endpoint login ตามบทบาทและตรวจบัญชี/รหัสผ่านใน Oracle ผู้โดยสารใช้ฟังก์ชันจอง คนขับใช้ฟังก์ชันปฏิบัติงาน และ admin จัดการข้อมูลตาม permission

30ระบบเก็บรหัสผ่านอย่างไร และเพราะอะไร?

แนวตอบ: เก็บ password hash ด้วย scrypt และ salt ไม่เก็บรหัสผ่าน plain text ตอน login นำค่าที่รับมา verify กับ hash แทนการเทียบข้อความที่เก็บตรง ๆ

31หลังล็อกอิน token ถูกใช้อย่างไร และ logout ทำอะไร?

แนวตอบ: API คืน bearer token เว็บเก็บใน sessionStorage และแนบ Authorization header กับคำขอที่ต้องยืนยันตัวตน logout เรียก API เพื่อลบ session และล้าง token ฝั่งเว็บ

32หน้าเว็บซ่อนปุ่มแล้วเพียงพอสำหรับความปลอดภัยหรือไม่?

แนวตอบ: ไม่พอ เพราะผู้ใช้เรียก API เองได้ Server จึงต้องตรวจ token บทบาท และสิทธิ์จากฐานข้อมูลอีกครั้งทุก endpoint ที่สำคัญ

หัวข้อ 9 · ตารางเหลือง

Dynamic RBAC: เพิ่ม ลบ แก้ไข และค้นหาสิทธิ์

กำหนดสิทธิ์ตามตำแหน่งและหน้าจอ

33RBAC ในระบบนี้ผูกความสัมพันธ์กันอย่างไร?

แนวตอบ: พนักงานมีตำแหน่ง ตำแหน่งเชื่อมกับหน้าจอผ่าน ROLE_PERMISSION แต่ละคู่กำหนด CAN_VIEW และ CAN_EDIT จึงจัดการสิทธิ์ตาม role แทนการกำหนดผู้ใช้ทีละคน

34ความต่างระหว่าง CAN_VIEW กับ CAN_EDIT คืออะไร?

แนวตอบ: CAN_VIEW อนุญาตให้เข้าดู ส่วน CAN_EDIT อนุญาตให้เปลี่ยนข้อมูล การแก้ไขควรต้องมีสิทธิ์ดูด้วย และ API ตรวจ CAN_EDIT ก่อนเขียนข้อมูล

35ถ้าเพิ่มสิทธิ์คู่ตำแหน่ง–หน้าจอที่มีอยู่แล้ว ระบบจัดการอย่างไร?

แนวตอบ: ใช้ upsert/MERGE ถ้ามีคู่เดิมจะอัปเดต ถ้าไม่มีจึง insert ช่วยไม่ให้เกิด permission ซ้ำสำหรับคู่เดียวกัน

36การกดลบสิทธิ์ลบแถว ROLE_PERMISSION จริงหรือไม่ และค้นหาได้อย่างไร?

แนวตอบ: ใน UI ปัจจุบันเป็นการซ่อนด้วย WEB_HIDDEN_RECORD ไม่ได้ DELETE แถวจริง การค้นหากรองชื่อ role ชื่อหน้าจอ หรือ screen code และ API ไม่นับ permission ที่ถูกซ่อน

จัดการพนักงาน: เพิ่ม ลบ แก้ไข และค้นหา

Employee CRUD และข้อควรระวังเรื่องการลบ

37เมื่อเพิ่มพนักงาน ระบบตรวจและบันทึกอะไร?

แนวตอบ: ตรวจชื่อ username รหัสผ่านอย่างน้อย 8 ตัวอักษร รูปแบบอีเมล รวมถึงแผนกและตำแหน่ง จากนั้นสร้าง employee ID และ hash รหัสผ่านก่อน INSERT ลง Oracle

38แก้ไขข้อมูลพนักงานโดยไม่เปลี่ยนรหัสผ่านได้ไหม?

แนวตอบ: ได้ ถ้าไม่กรอกรหัสผ่านใหม่ ระบบคง hash เดิมไว้ ถ้ากรอกรหัสใหม่จะตรวจความยาวและสร้าง hash ใหม่ก่อนบันทึก

39ปุ่มลบพนักงานลบข้อมูลถาวรหรือไม่?

แนวตอบ: ปัจจุบันเป็นการซ่อนรายการจากหน้า admin ด้วย marker ไม่ได้ลบแถว EMPLOYEE และไม่ได้ปิด IS_ACTIVE อัตโนมัติ จึงต้องอธิบายตามจริงและถือเป็นจุดที่ควรปรับถ้าต้องการปิดบัญชี

40ค้นหาพนักงานได้จากอะไร และจะสาธิตอย่างไร?

แนวตอบ: ค้นจากรหัส ชื่อ username เบอร์โทร อีเมล ตำแหน่ง หรือฝ่ายได้ สาธิตโดยพิมพ์คำบางส่วน ตรวจผลลัพธ์ แล้วแก้ข้อมูลพนักงานและโหลดรายการใหม่ยืนยันการบันทึก

จุดที่ควรตอบอย่างตรงไปตรงมา: “ลบ” พนักงาน/สิทธิ์ในบางหน้าคือซ่อนจากหน้าเว็บ ไม่ใช่ลบแถวจริง; จำนวนผู้โดยสารจริงอิงการเช็กอินและ seat_count; ข้อมูลชื่อหรือรถที่ติดคำว่า TEST/DEMO เป็นข้อมูลสาธิต ไม่ใช่ข้อมูลจริง

โครงสร้างคำตอบที่ดี

  1. บอกสิ่งที่ผู้ใช้ทำ: เช่น เลือกเที่ยวและจุดขึ้น–ลง
  2. อธิบาย validation: เช่น cutoff 20 นาที ความจุ และลำดับจุดจอด
  3. บอกจุดที่ตรวจจริง: UI ช่วยใช้งาน แต่ API ตรวจซ้ำก่อนเขียน Oracle
  4. สาธิตผลลัพธ์: แสดงสถานะ รายการในฐานข้อมูล หรือ API response
  5. บอกข้อจำกัดโดยไม่กล่าวเกินจริง: เช่น การซ่อนข้อมูลไม่ได้แปลว่าลบถาวรหรือปิดบัญชี
ตัวอย่างประโยคปิด: “ระบบตรวจเงื่อนไขทั้งหน้าเว็บและ API โดย API เป็นจุดบังคับใช้จริงก่อนบันทึกฐานข้อมูล ส่วนจุดที่ยังไม่รองรับ เช่น การยืนยันการลงรถจริง จะแยกเป็นงานพัฒนาต่อไปครับ/ค่ะ”
